# WPMS Architecture (DRAFT for approval)

## Scope
Release 1: auth/RBAC, employees, picking and packing tasks, CSV import, dashboards/reports with CSV export, audit trail, admin config, backup/recovery docs. **Out of scope:** Excel import, Uniware API, CCTV (Phase 2 hooks in schema only), covert monitoring of any kind.

## Stack and constraints
PHP 8.0+ minimum, written to run clean on **8.4** (user reports Z.com runs 8.4.27; not yet verified by me), MariaDB 10.4+/MySQL 8, PDO, sessions, Bootstrap (vendored locally under `assets/vendor/`, no CDN dependency for warehouse PCs), vanilla JS. No Composer/Node on the server. Same layout and installer pattern as `barangay-locator`.

## Task workflow
States: `pending -> in_progress -> completed`; `pending|in_progress -> cancelled`. No other transitions.
- Start: sets `started_at = NOW()` server-side (clients never supply times), requires assignee.
- Complete: transaction; row locked (`SELECT ... FOR UPDATE`), sets `completed_at`, computes `duration_seconds`, requires item quantities.
- Completed/cancelled rows are immutable except via a **correction**: reason mandatory, old/new values written to `task_events`, `row_version` incremented. Every transition writes a `task_events` row in the same transaction.
- `row_version` gives optimistic locking against concurrent edits.
- Imported historical tasks may carry supplied start/complete times; they are flagged `source='import'`.
- Barcode scanners that act as keyboards: SKU/order inputs accept Enter-terminated input; entry method (`scan`/`manual`) recorded per item.

## CSV import
Upload -> validate extension/size/MIME -> store under private `storage/imports/` with random name + SHA-256 -> parse -> per-row validation -> **preview** (valid / invalid / duplicate counts, per-row reasons) -> user confirms -> single transaction commit -> summary and downloadable rejection CSV. Nothing touches `tasks` before confirmation. Same file hash re-upload warns. Row duplicates detected by `external_key = sha256(activity|order_number|sku|employee_code|completed_at)` (UNIQUE) and within-file duplicates.

**Uniware context (user-supplied description, not a sample file):** pickers are Uniware users identified by email/username (fields: Name, Email, Phone, Username, Added On, Status, Role). A picklist ("picking task") has Picklist Code (PT-prefixed), Picked By, Generated By, Status (CREATED → PENDING → IN_PROGRESS → COMPLETED), Type and Shipment ID (LOCA-prefixed), with created/completed timestamps and created-by/completed-by. Picker -> Picklist -> Shipment -> Order items. Mapping: `Picked By` -> `employees.uniware_username`; `Picklist Code` -> `tasks.picklist_code`; `Shipment ID` -> `tasks.shipment_id`; CREATED/PENDING -> `pending`; raw status kept in `external_status`.

Template columns (proposed working version; **column names and date format still to be matched to a real Uniware export**): `picked_by, picklist_code, shipment_id, type, status, generated_by, created_at, completed_at, warehouse_code, sku, product_description, quantity` (+ packing columns once a packing export sample is seen). Dates `YYYY-MM-DD HH:MM:SS`, Asia/Manila. UTF-8, comma-delimited; row/size limits from settings and verified host limits. `external_key = sha256(activity|picklist_code)`: one WPMS task = one Uniware picklist; its shipment/order/SKU lines become `task_items` (which carry `shipment_code`, `order_number`, `sku`, `quantity`). Rows sharing a picklist code are grouped into one task on import.

**Source of the Uniware description:** `Gingersnaps-Warehouse-System/unicommerce-data-extraction.md` (UI observation by the Bolt agent, 24 Oct 2026). It is **not** an export file. Uniware's own start time is "inferred, not shown"; export columns come from Tasks > Subscription export jobs and have not been seen. **The sample picklists in that document have type `PUTAWAY_GATEPASS_ITEM` (inbound putaway), not outbound order picking.** **Decision (user, 24 Oct 2026): scope is outbound order picking and packing only. Putaway/inbound tasks are out of scope.** The importer takes an allow-list of Uniware task types from settings (`import_allowed_types`); rows with any other type (including `PUTAWAY_GATEPASS_ITEM`) are rejected with the reason "type not in scope". The exact Uniware type value(s) for outbound picking and packing are still unknown and must come from a real export; the allow-list stays empty (import blocked) until set.

That file (supplied by the user, 24 Oct 2026) has placeholder values (`PT-SAMPLE-001`, `SKU-ASMR-001`), formats that differ from real codes seen earlier (`PT60185`, `LOCA23638`, `112191_WFR`), and 3 rows. **Treat it as a structure sketch, not a verified export.** Do not finalise the importer until a real export is checked against it.

| Operations | ignored | UI action labels |

Gaps this file exposes:
1. **No quantity column.** Assumption (unverified): each row is one unit, so `qty_expected = 1` unless an optional `Quantity` column is present.
2. **No picklist "Type" column**, so the type allow-list cannot work on this layout. Proposed scope rule instead: import only rows with a non-empty `Sale_Order_Code` (outbound sales orders), and reject the rest as "not an outbound order row". Needs confirmation against a real export.
3. **No packing data** (no packer, packing status or packing times). Only `Shipping_Package_Code` exists, so packing tasks cannot be imported from this layout; packing would be timed in WPMS only until a packing export is seen.
4. **No warehouse column**: the warehouse is chosen on the import screen.
5. **No start time**, as already noted.
6. `ISO 8601` parsing is needed in addition to `Y-m-d H:i:s` (`parse_datetime` does not accept `T`/`Z` yet).

**Important:** a Uniware export gives created and completed times, not when the picker actually began. Imported tasks therefore get `started_at = NULL` and no `duration_seconds`; created→completed includes queue time and must not be presented as picking time. Imported data supports counts, units, and error/throughput-per-day metrics; time-per-task metrics come only from tasks timed in WPMS (Start/Complete) or from an export that has a true start time.

## Security
Argon/bcrypt via `password_hash`; `session_regenerate_id` on login; Secure/HttpOnly/SameSite cookies; idle and absolute timeouts; login throttling and lockout (`failed_logins`, `locked_until`); CSRF token on every POST; PDO prepared statements with emulation off; output escaping; CSP and security headers as in barangay-locator; uploads never executable and stored outside the web root where possible; audit log excludes secrets; generic login errors; forced password change on first login.

## Deployment safeguards (summary; full guide written after hosting is verified)
Separate DB and least-privilege DB user; no access to the Warehouse Inventory System files/DB; no DROP statements in any shipped SQL; installer refuses a non-empty database that lacks WPMS tables; backups (mysqldump from cPanel Backup/phpMyAdmin export + file zip) before upgrades; HTTPS verified; deny rules verified by actually requesting protected URLs.
