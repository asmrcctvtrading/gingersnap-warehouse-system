Risk Register
# Risk Likelihood Impact Mitigation
R1 DEV-004 (GRN) takes longer than 2 sprints
GRN is the most complex module and gates all downstream P1 work. Schema design decisions may require rework. 		High High
  • Split into explicit Part 1 (schema + list + form) and Part 2 (view + print) across two sprints
  • Lock schema design in the first 2 days of S2 — no scope creep after Day 2
  • DEV-002/003 stubs protect S1 delivery from GRN delays
R2 CSV migration data quality issues
grn.csv (3.4 MB) and putaway.csv (3.4 MB) likely have inconsistent references, NULL values, or encoding issues that break automated import. 		High Medium
  • Run data profiling (column types, NULL %, distinct values) before S5 begins
  • Build import scripts with dry-run mode that reports errors without committing
  • Allocate buffer days (S5 has +1 day buffer built into estimates)
  • Keep original CSVs archived permanently
R3 Single-person bottleneck
If the same person is both Developer and DBA, context-switching adds overhead and illness/unavailability stalls the entire project. 		Medium High
  • Maintain written sprint notes so work can resume after gaps
  • DB schema changes documented in migration SQL files (already established)
  • Sprint 1 buffer (only 7 pts) gives slack for the heavier sprints ahead
R4 Production DB changes break live data
ALTER TABLE operations in S6 (tickets, gatepass_items) run against tables with existing production data. 		Medium High
  • Full DB backup before every ALTER TABLE (mandatory, automated)
  • Test all migrations on a staging clone first
  • All new columns use NULL or DEFAULT — never NOT NULL without default
  • Schedule maintenance window (off-peak hours) for S6 DB changes
R5 Scope creep from stakeholder feedback post-S4
Once the P1 workflow is live, end users will request changes that could delay S5–S8. 		Low Medium
  • New requests go to a backlog (DEV-021+) — nothing enters current sprint without explicit reprioritization
  • S8 has a natural buffer week built in for UAT feedback fixes
  • Communicate the go-live plan to stakeholders before S5 begins

Go-Live Checklist — Conditions to Retire Google Sheets

All of the following must be true before Google Sheets is archived as read-only:

1
All P1 modules are live and tested in production
GRN, QC Inspection, and Putaway modules all accessible, working, and confirmed by the warehouse team (not just the developer).
2
All historical CSVs have been imported and reconciled
grn.csv, putaway.csv, po.csv, and output.csv fully migrated. Row counts match. No unresolved import errors.
3
Tickets module has CTRL auto-numbering and all required columns
DEV-011 and DEV-012 complete. Existing tickets backfilled with CTRL numbers. No new tickets created in Sheets.
4
Dispatching Priority and Inspection Priority reports match GS output
A side-by-side comparison of both systems for the same date range shows <5% variance on all key figures.
5
WIP Status and all existing reports load without errors
DEV-008 confirmed. All reports tested with real production data. No blank pages, no PHP warnings visible.
6
At least 1 full week of parallel operations completed
For 5 business days, all transactions entered in both PHP and Google Sheets simultaneously. End-of-week reconciliation confirms data parity.
7
All user roles are set up and tested in production
Admin, Warehouse, QC Inspector, Supervisor, and Manager roles all have the correct access. No user can accidentally access a module above their permission level.
8
Database backup schedule is active
Automated daily backup confirmed running on the production server. Most recent backup is <24 hours old and restore has been tested at least once.
9
Go-Live sign-off from the warehouse manager / owner
The person accountable for warehouse operations has reviewed the system, tested key workflows, and formally agreed the PHP system meets operational needs.
10
Google Sheets archived (not deleted) with a clear "READ-ONLY — Retired [Date]" notice
Sheets are not deleted. They are moved to an archive folder and marked read-only. Access is retained for at least 6 months as an emergency reference.
Capacity note: Sprint point estimates assume 70% developer capacity per 2-week sprint (~7 productive days). Story points are calibrated as: 1 pt ≈ 1 hour of focused work for small tasks, 1 pt ≈ 0.5 days for module-level work. The 86-point total across 8 sprints is achievable for a 1–2 person team over 16 weeks at this capacity. If velocity is higher in early sprints, S7 and S8 items can be pulled forward.
